Tennis Architecture — Self-Review & Open Questions
===================================================

─────────────────────────────────────────────────────────────────────────────
ARCHITECTURE FEEDBACK (self-critique)
─────────────────────────────────────────────────────────────────────────────

BUGS / DESIGN GAPS

1. Ball.step() bounce detection is imprecise.
   Adding vz then checking z <= 0 lets the ball overshoot below ground.
   Fix: when z + vz would cross 0, clamp z=0 and apply bounce in the same tick.
   Otherwise ball visually dips underground for one frame and collision checks
   fire a tick late.

2. Direction normalization in Ball.applyHit() is unspecified.
   "Normalize to speed" requires a length calculation. Integer sqrt is expensive
   and imprecise. Need to commit to an approach now or devs will invent their own:
     Option A: octant-based (8-dir snap; dx/dy = ±1 or 0)
     Option B: Chebyshev normalization: divisor = max(abs(dx), abs(dy))
     Option C: pre-defined target positions (baseline corners, service box center)
               so direction is always one of ~8 fixed vectors
   Option C fits determinism best and removes normalization entirely. Recommend it.

3. tryHit() is a pure query; clearPendingAndStartHitstop() is a separate call.
   Risk: caller forgets the second call. These two are always paired.
   Consider: make tryHit() mutating and clear pendingShot + set hitstop internally.
   The "pure query" purity isn't bought by anything here.

4. HumanController receives opponentPos on every tick() call.
   Only needed for auto-aim target computation, which only fires when a shot is
   committed. Passing it every tick creates coupling. Pass only when building target.

5. CPU in .serveInFlight phase — receiver movement undefined.
   HumanController.tick() blocks movement in .serving(.bottom) but says nothing
   about .serveInFlight. The human receiver should be free to move during
   serve flight. Needs explicit branch in HumanController.tick().

6. OpponentAI drop shot fires on tick % 5 == 0.
   This is deterministic but creates a learnable pattern. Skilled player
   stands deep every 5 ticks and it becomes exploitable. Use a seeded LCG
   counter instead (still deterministic, not cycle-predictable):
     dropChance = (tick * 2654435761) >> 28  (Knuth multiplicative hash)

7. scoreFlashTimer ticks down in draw(), not logic().
   This means it won't advance in headless mode unless draw() is called.
   Headless milestones do call draw (screenshots), so probably fine.
   But if anyone ever runs logic-only tests, flash state won't clear.
   Low priority; note it.

8. Ball.trailHistory stores screen coords (already /100).
   Everything else on Ball is fixed-point. This inconsistency is intentional
   (trail is visual-only) but needs a comment or it WILL confuse a dev.

9. No matchEnd restart path defined.
   Scene goes idle on .matchEnd. Nothing triggers restart or menu transition.
   TennisScene needs either a restart() method or a delegate/callback so
   TennisApp can respond. Without it, the game soft-locks at match end.

10. ResourceIds only covers 3 assets (playerBottom, playerTop, ball).
    With PlayerAnimState, actual MVP needs (2 players) × (4 anim types) × (4 frames)
    = up to 32 URLs. Even pointing all to same placeholder, loading must iterate them.
    Either load one placeholder and reuse its ImageFlyWeight, or define the full
    ResourceIds struct now so the art swap is mechanical. Current doc is ambiguous.

11. Serve diagonal rule unspecified.
    Real tennis: server targets diagonally opposite service box
    (deuce court → opponent's deuce court, etc.). Architecture assumes center-of-net
    serve position and "receiver's near service box." If the court ever shows which
    side the server stands on, this breaks. Decide now: always center, or model sides?

12. Ball.applyHit() spin stat affects topspin and slice differently.
    The formula adjusts spinBounceMult for both via stats.spinBounceMult().
    But slice is reduced by spin stat too — high spin = worse slice (less skid)?
    That's counterintuitive. Topspin and slice should scale differently from
    the spin stat. Needs separate spinBounceMult and sliceSpeedMult derivations.

13. HitResult is transient but constructed in tryHit().
    tryHit() is called for both player and opponent each tick. If both are in
    hit range simultaneously (theoretical but possible during exchange at net),
    both return a HitResult. TennisScene processes player first then opponent.
    The second applyHit overwrites the first. Is that right? Probably yes —
    last hitter wins. But it should be explicit, not accidental ordering.

OPEN QUESTIONS — GAME DESIGNER
─────────────────────────────────────────────────────────────────────────────

SHOT SYSTEM

GD-1. Failed sequential input fallback.
      Player presses A, waits, sequence window expires, then presses A again.
      Does the second A fire a topspin immediately, or is there a brief lockout?
      If no lockout, rapid A-A could feel identical to a single A.

GD-2. Charge visual feedback.
      Does the player sprite change pose during charge hold, or only the charge bar?
      A sprite pose change (e.g., wind-up frame) reads better at 160×144 than
      a HUD bar alone. But it requires a charge frame per direction (8 dirs × pose).
      Worth it?

GD-3. Post-sequence shot result on misfire.
      If player presses A→B but the B comes slightly late (outside sequence window),
      what fires? The A is already consumed. Does a standalone B (slice) fire,
      or nothing? "Nothing" feels broken; "slice" may surprise the player.
      Recommend: B fires slice on window expiry. Needs to be in spec.

GD-4. Lob return eligibility.
      Is a lob always an overhead smash opportunity for the receiver, or can they
      also return it with a normal groundstroke if they're positioned correctly?
      High lob + player near baseline = smash eligible? Or must lob always be
      returned as topspin/slice if player isn't in smash position?

GD-5. Drop shot bounce behavior.
      Spec says "very low second bounce distance." Does the drop shot bounce at all
      visually, or does it just die near the net? Current model: bounceHeight=150,
      postBounce=10, so it barely moves after first bounce. Is this readable or
      will players think the game froze?

GD-6. Simultaneous exchange at net.
      Both players in hit range of ball at same time (e.g., both at net).
      Current behavior: player hit takes priority (processed first). Should this
      be a special interaction (volley duel?), or is the priority rule fine?

GD-7. Hitstop scope.
      Both players freeze on any hit (current design). Does this feel punishing
      if the CPU lands a hard smash and the player is frozen while the ball
      travels past them? Alternative: only hitter freezes briefly. What's intended?

COURT / READABILITY

GD-8. Ball z scale.
      At 160×144, how high should a lob appear visually? Current arcHeight=6000
      (60 screen pixels at peak) would push the ball off-screen top or clip near
      the net visually. Need to validate scale against the actual court rect (124px tall).
      Suggest a visual pass before finalizing arcHeight values.

GD-9. Trail persistence.
      Should the trail clear on bounce, or linger for N ticks after?
      Clearing on bounce is simpler; lingering reads better. Current: trail pushes
      on bounce (3 entries). After bounce entries are ground-level, which looks odd.
      Maybe only draw trail while ball.z > threshold?

GD-10. Service box legality visualization.
       Should the service box flash or highlight on an illegal serve?
       At 160×144 a text message ("FAULT") may be more readable than a flash.
       Needs a decision — it's a draw call and a timer.

─────────────────────────────────────────────────────────────────────────────
OPEN QUESTIONS — PRODUCT MANAGEMENT
─────────────────────────────────────────────────────────────────────────────

SCOPE

PM-1. Match restart / return to menu.
      After matchEnd, what happens? Options:
        A. Auto-restart same match (simplest for milestone testing)
        B. Return to surface select screen
        C. Hold on result screen; await button press
      Without a decision, we will implement A by default.
      This affects whether TennisScene needs a delegate or just a restart() method.

PM-2. Surface selection for MVP.
      Is surface hardcoded to Hard Court for first playable, or does the player
      choose before the match? A surface select screen is spec'd for M5 menus.
      If selection is needed earlier for testing/demo, we should know now.

PM-3. Second human player (local multiplayer).
      Architecture supports two TennisPlayer instances and symmetric controllers.
      Adding HumanController for both players is a ~1-day add-on.
      Is local 2P in scope for any milestone before Release 2?

PM-4. Headless screenshot acceptance.
      Milestone acceptance currently requires "short screen recording."
      Headless mode can produce screenshots but not video.
      Are screenshots acceptable, or do we need a video pipeline?
      If video: scope that separately; it's not in the current architecture.

PM-5. First playable target date.
      Affects whether surface tuning and OpponentAI polish happen before or after
      internal demo. If a hard date exists, M3 (shot system) is the critical path
      milestone. Knowing the date lets us flag risk early.

PM-6. Player stat preset selection.
      Spec ships with Balanced and Power presets. Is there a character select screen
      in MVP, or does the human always use Balanced and CPU uses Power?
      If always fixed, remove the preset selection from MatchConfig for now.

PM-7. Score display legibility.
      At 160×144 with no dedicated font, score must use sprite numbers or the
      engine's TTF font support. Current design assumes TTF via AtlasLoader.
      Confirm: is a system font acceptable for score display, or do we need
      pixel art number sprites? This affects ResourceIds and loadResources scope.

PM-8. Audio hooks.
      Spec reserves audio hooks (hit, bounce, score stinger).
      Architecture has no audio layer. Is placeholder silence acceptable for
      all milestones, or does M4 need at least one sound to ship?
